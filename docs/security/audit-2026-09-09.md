# Audit accessibilité et sécurité — 9 septembre 2026

## Périmètre et méthode

L’audit porte sur l’accueil, le catalogue, la recherche avec et sans résultat, la fiche et son formulaire, les quatre pages transverses et la 404. Les mesures navigateur utilisent Chrome headless, Playwright et axe sur les images de production Nginx/Express, avec MySQL en tmpfs. Les vues sont contrôlées à 320, 375, 768 et 1440 pixels. Les chargements, pannes et validations du formulaire sont aussi exercés.

La vérification du reflow à 400 % utilise un viewport de 320 pixels CSS, équivalent à une fenêtre de 1280 pixels agrandie à 400 %. Le redimensionnement du texte à 200 % est testé séparément à 768 pixels et les captures ont été relues visuellement. Cela ne remplace pas une manipulation du zoom natif dans plusieurs navigateurs.

Les simulations d’envoi de formulaire ne délivrent aucun courrier. Les tests MySQL utilisent leur propre projet Docker et une double garde de nom de base et de mode test. Aucun volume de données utilisateur n’est supprimé.

## Écarts corrigés

| Constat | Correction et preuve |
| --- | --- |

| Navigation SPA laissant le focus sur un contrôle masqué | Focus sur `main` lors du changement d’URL ; lien d’évitement et menu testés au clavier |

| Deux zones de recherche non distinguables | Noms accessibles propres au menu et à l’accueil ; axe avec menu ouvert et sur ordinateur |
| Fiche précédente conservée après changement de slug | État de requête et formulaire remontés pour chaque slug ; test de non-régression |
| Colonnes trop étroites avec texte agrandi à 200 % | Grilles adaptatives en `rem`, recherche repliable et captures revues |
| Focus insuffisant sur certains fonds et textarea | Anneau bicolore, focus du textarea et bordures de champs contrastées |
| JSON invalide ou volumineux renvoyant 500 | Réponses 400/413/415 neutres, quotas avant parsing ; tests HTTP |
| CR/LF terminaux supprimés avant validation SMTP | Contrôle avant normalisation ; test d’injection aux extrémités |
| Absence d’en-têtes de sécurité Nginx | CSP, HSTS conditionnel, nosniff, permissions, referrer et frame policy sur pages, actifs et erreurs |

| Pas de sortie réseau pour SMTP en production | Réseau `egress` backend distinct, sans publication du backend |
| SMTP pouvant continuer sans STARTTLS | TLS obligatoire en production ; test sur un serveur local refusant STARTTLS |
| Paquets vulnérables dans les images de base | Correctifs système, retrait de npm/Corepack et MySQL Shell inutilisés |

## Analyse des images

Trivy **0.74.0**, téléchargé depuis sa [publication officielle](https://github.com/aquasecurity/trivy/releases/tag/v0.74.0) et contrôlé par SHA-256, a d’abord signalé des alertes dans les images de base :

| Image avant correction | Critiques | Hautes |
| --- | ---: | ---: |
| Frontend | 0 | 35 |
| Backend | 1 | 12 |
| Base | 1 | 37 |

Les correctifs Alpine éliminent les alertes système des deux applications. npm embarqué par Node portait notamment des alertes sur `tar` ; il a été retiré de l’image d’exécution. La mise à jour Oracle Linux et la suppression de MySQL Shell éliminent les alertes système et Python de la base. Le serveur MySQL reste celui de l’image 8.4 choisie.

Après correction : **aucune alerte Trivy dans les images frontend et backend**. L’image de base conserve **46 alertes de version liées uniquement à la bibliothèque standard Go du binaire gosu** : 1 critique, 21 hautes, 21 moyennes, 2 basses et 1 inconnue.

### Qualification des alertes gosu

Le binaire exact installé, `gosu 1.19`, porte l’empreinte :

```text
52c8749d0142edd234e9d6bd5237dff2d81e71f43537e2f4f66f75dd4b243dd0
```

`govulncheck v1.1.4 -mode=binary` a été exécuté dans un conteneur Go isolé sur ce binaire. Résultat : **aucun symbole vulnérable détecté** ; 3 vulnérabilités existent dans des paquets importés et 42 dans des modules requis, mais les fonctions concernées ne sont pas appelées selon cet outil. Le résultat brut est conservé dans `gosu-vulncheck.txt`.

Ces alertes Trivy concernent notamment TLS, certificats, HTTP, parsing d’e-mails, XML et templates. Le programme sert ici uniquement à passer de root à mysql puis à exécuter le serveur, avec des arguments d’entrypoint fixes. Sa [politique de sécurité officielle](https://github.com/tianon/gosu/blob/1.19/SECURITY.md) recommande précisément de vérifier les appels vulnérables avec govulncheck au lieu de conclure à partir de la seule version de Go.

Les **22 alertes hautes/critiques** sont qualifiées dans [image-exceptions.json](image-exceptions.json), avec identifiants exacts, cible, paquet, version et empreinte. La commande d’audit vérifie l’empreinte directement dans l’image analysée. L’exception expire le **9 octobre 2026** ; toute nouvelle alerte haute/critique ou tout changement de binaire fait échouer le contrôle. Les alertes brutes restent visibles dans les rapports : elles ne sont pas effacées du scan.

## Contrôles humains et limites

| Vérification | État |
| --- | --- |
| Revue du code sémantique, labels, focus, statuts et titres | Effectuée |
| Clavier dans Chrome : évitement, menu, Échap, navigation et formulaire | Exercé par commandes clavier Playwright |
| Captures accueil et fiche avec texte agrandi | Relues visuellement après correction |
| Lecteur d’écran réel : Orca, NVDA ou VoiceOver | À effectuer par une personne ; aucune validation auditive revendiquée |
| Zoom natif 200/400 %, Safari/Firefox et appareil tactile | Recette humaine complémentaire à effectuer |
| Validateurs HTML/CSS sur DOM final et styles compilés | À compléter ; axe et TypeScript ne sont pas des validateurs W3C |
| Traefik réel, certificat public, redirection HTTPS, SMTP du fournisseur | Recette d’hébergement à effectuer |

La présence de `aria-live` et l’absence de violations axe ne prouvent pas que les annonces sont satisfaisantes avec toutes les combinaisons lecteur d’écran/navigateur. Ne pas publier de déclaration de conformité complète sur la seule base de ces résultats.

Les quotas utilisent une mémoire locale au processus ; un déploiement à plusieurs instances demanderait un stockage partagé. L’API publique demeure utilisable par des clients HTTP malgré les restrictions de navigateur. MySQL communique sur un réseau Docker interne, sans TLS applicatif configuré entre Express et la base ; une séparation sur plusieurs hôtes demanderait du chiffrement authentifié. Les journaux et sauvegardes doivent recevoir une politique de conservation sur l’hébergement. Le contrôle des secrets utilise des signatures usuelles et l’exclusion des fichiers locaux ; il ne garantit pas l’absence de tout secret arbitraire dans l’historique.
